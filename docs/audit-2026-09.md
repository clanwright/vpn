Владелец разрешил доработку всех восьми аудитов: код, пакеты, контракты,
клиентские профили, документация, независимое ревью и полный оставшийся gate.

Nix assertion должен вычислиться; список derivations не доказывает прохождение.

Репозиторная реализация, интеграция и независимое source review завершены.
Полный оставшийся gate прошёл. Владелец 9 сентября принял ограничение
клиентского DNS Mihomo, описанное ниже. Согласованный репозиторный проход

## Клиентская политика

- Selective защищает списки блокировок в обе стороны, необходимые зависимости
  и постоянные дополнения consumer. Полные Google/AI/dev категории не добавляются
  ради отдельных доменов. Личная policy задаётся consumer, а не зашивается в библиотеку.
- Full направляет интернет-трафик через выбранную VPN-пару. LAN, router и
  Tailscale остаются DIRECT в обоих режимах.
- Выбор режима и точной пары server–protocol независим между selective и full.
  Manual не переключается автоматически при отказе выбранной пары.
- Auto использует штатное поведение ядра. Native latency/status — ограниченный
  health signal; HTTP HEAD не доказывает передачу payload, upload или UDP relay.
- Защищаемые приложения и web не получают скрытый DIRECT при отказе всех VPN.
  В selective незатронутый политикой трафик остаётся DIRECT. Пользователь может
  явно отключить VPN.
- Naive остаётся отдельным sing-box-профилем: обычный Mihomo HTTP CONNECT не
  воспроизводит Naive padding/Chromium transport. Для защищаемого Naive-трафика
  UDP отклоняется; без доступного устройству Naive endpoint файл, HTTP handler
  и ссылка sing-box-профиля не публикуются.
- Настройка роутера, установка приложений, OS kill switch и импорт merged config
  не выполняются этим репозиторием. Список возможностей core не доказывает,
  что конкретное установленное приложение уже использует нужную версию.

Mihomo Global обходит обычные routing rules. Его нельзя использовать как
согласованный full-режим, если при этом теряются private DIRECT exceptions.
Профили должны выражать full через обычную policy с private rules перед
заключительным VPN-правилом. Для sing-box применимы native `clash_mode` rules.

## DNS, фильтрация и данные

Основной серверный путь — AdGuard Home → рекурсивный loopback Unbound.
AdGuard может стартовать независимо от готовности Unbound. Резерв AdGuard
указывает на постоянный native dnsproxy, а не на плоский смешанный список:

1. Cloudflare Standard, Quad9 `9.9.9.10` без threat blocking и Google Public DNS
   параллельно по зашифрованным каналам;
2. лишь после транспортных ошибок всех encrypted exchanges — plaintext
   `1.1.1.1`, `9.9.9.10`, `8.8.8.8`.

Яндекс исключён из всех резервов. Полученные NXDOMAIN/SERVFAIL, в том числе
DNSSEC rejection, завершают обработку и не открывают менее защищённую ступень.
DNSSEC включён на основном пути; encrypted providers выбраны с validation.
Quad9 включил DNSSEC на `.10` с 15 июня 2026 согласно
[объявлению от 9 апреля](https://quad9.net/news/blog/quad9-enables-dnssec-on-all-service-endpoints/);
[текущая матрица](https://quad9.net/service/service-addresses-and-features/)
сохраняет для этого адреса отсутствие threat blocking и ECS. Старые setup guides
с пометкой «No DNSSEC» не описывают выбранную сентябрьскую политику.
Plaintext — согласованный аварийный компромисс: он не обещает шифрования или
защиты ответов от вмешательства на пути. Domain names становятся видны
провайдеру. Это исключение касается DNS, а не DIRECT для защищаемого web/app.

Серверный dnsproxy не переключает VPN и не помогает клиенту при полном отказе
AdGuard. Клиентский резерв — отдельная функция. Прямой encrypted/plaintext DNS
при отказе AdGuard согласован; фильтрация AdGuard при обходе временно теряется.

Точный sing-box 1.14 поддерживает нужный порядок через `evaluate`, response
matching, `race` и `respond`: transport error оставляет запрос для следующего
правила, любой полученный ответ завершает соответствующую ступень. Этот вывод
проверен по [dns/router.go v1.14.0](https://github.com/SagerNet/sing-box/blob/v1.14.0/dns/router.go),
а не по общему названию fallback. Порядок фактических сетевых запросов не
проверяется в согласованном gate.

**Принятое ограничение Mihomo (9 сентября):** его `nameserver`/`fallback` используют параллельные
пулы и фильтрацию ответов; строгий transport-error-only каскад ими не выражается.
Владелец подтвердил основной AdGuard как единственный клиентский DNS Mihomo,
без клиентского резерва и без дополнительного локального resolver. При отказе
AdGuard новые запросы без подходящего ответа в кэше не получают резервного
разрешения. Серверный dnsproxy reserve и строгий клиентский каскад sing-box
сохраняются. Это принятие уже проверенной реализации, а не изменение кода.

Сохраняются parental control, Safe Search, HaGeZi Multi NORMAL + URLHaus.
Удалённый Safe Browsing выключен. Личные allow/deny rules остаются
декларативными consumer inputs, без обязательного редактирования UI.
Stale выдаёт только Unbound; AdGuard `cache_ttl_min=0` и
`cache_optimistic=false`, dnsproxy cache выключен.

Query log хранится 7 дней без IP-анонимизации, statistics — 90 дней. Политика
journal/Caddy logs не получает произвольных новых сроков. Общий публичный DoH
может обслуживать посторонних; индивидуальные ClientID/auth не требуются.
Это не открывает WAN plain DNS, UI или backend ports. Точные адреса и домашняя
привязка DNS на роутере принадлежат будущей consumer composition.

## Доказательная база и пределы

Исходный снимок — ревизия `06b5652b932a9779931088626c60279618850505`,
исследование 7 сентября. Доработки и проверка точных источников — 8 сентября.
Исторические parser/build/probe результаты не являются результатами нового
pure Nix gate и не оправдывают возвращение удалённых тестов.

В исходном исследовании на Mac отмечены Clash Verge 2.5.2 с Mihomo 1.19.29
и SFM 1.14.0 build 1 без установленной версии embedded core. Это прежний
снимок, не повторно подтверждённое текущее состояние. Android Clash Meta и
ImmortalWrt/Nikki не обновлялись. Для AWG3 нужен соответствующий core; возможности
[Mihomo 1.19.30](https://github.com/MetaCubeX/mihomo/blob/v1.19.30/adapter/outbound/wireguard.go)
нельзя приписывать установленной 1.19.29.

Причина сообщённого отказа Hysteria2 на Дом.ру, Т-Мобайл и Yota не установлена.
Новый Gecko-профиль — выбранная конфигурация, а не доказанное устранение
операторской блокировки. Одинаковые адреса, провайдеры и маршруты могут давать
общие отказы разных протоколов. Протокольная совместимость не равна доступности
из РФ, а работа туннеля не отменяет app-side VPN detection или exit-IP policy.

Consumer monitoring, эксплуатация, release и adoption остаются отдельными
действиями владельца. Mieru, AnyTLS, TrustTunnel и Sudoku остаются в
[бэклоге](backlog.md), без реализации в этом проходе.
