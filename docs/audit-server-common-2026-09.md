# Общие серверные настройки: аудит на 7 сентября 2026

## Статус

Исследование исходников и upstream-документации; ниже рекомендации для
обсуждения, не реализованные настройки. Серверы, firewall, пакеты и секреты
не менялись. Принятые протокольные решения находятся в
[основном аудите](audit-2026-09.md) и связанных документах.

VPN владеет реализацией модулей, контрактами, пакетами и локальными checks.
Consumer владеет размещением, exposure policy, мониторингом, привязками секретов,
операторскими действиями и TCP tuning. Network владеет общей сборкой Caddy.
Эти границы сохраняются; для аудита не создается отдельная система управления.

## Что подтверждено в текущем коде

| Область | Наблюдение | Последствие |
|---|---|---|
| Mihomo | Общий VLESS/Hysteria процесс от root, `Type=simple`, `Restart=on-failure`, задержка 2 секунды | Перезапуск есть; привилегии и отказы протоколов пока не разделены |
| Runtime config | Секреты подставляются в `/run`, config root-only; временные файлы Mihomo очищаются trap | Хорошая основа, но публикация через `install` не гарантирует атомарной замены |
| Запуск | Mihomo parser в preStart, ожидание bind address, listener check в postStart | Не проверяет auth, relay, сертификат на пути клиента и длительную передачу |
| Firewall | VLESS глобально разрешает порт, Hysteria использует destination-scoped rule | Уже найденное несоответствие контракта VLESS |
| DNS | Unbound наследует NixOS unit; есть отдельный check реального `READY=1` | Отсутствие unit options в addon не означает отсутствие upstream hardening |
| Зависимости | AdGuard зависит от успешного старта Unbound; Naive generator требуется общему Caddy | Отказ вспомогательного компонента может остановить внешнюю точку доступа |
| Проверки | Gate содержит static, flake evaluation, Linux checks и сборку пакетов | Доказывает свойства исходников, но не доступность развернутых серверов |

## Единый целевой подход к сервисам

Разделяем Xray и Hysteria2 согласно принятой архитектуре. Для каждого proxy
процесса — отдельный статический service user и доступ только к его runtime
конфигурации и нужному сертификату. Root-only generator может подготовить
файлы и выставить права для этого пользователя; оставлять config `0400 root`
и просто менять `User` нельзя. Группы не должны давать чтение всех VPN-секретов.

Для этих двух proxy units рекомендуем `NoNewPrivileges`, read-only системные
пути, закрытый home, отдельный временный каталог, запрет изменения kernel
tunables/modules/control groups и ограниченный capability set. При bind ниже
1024 нужен `CAP_NET_BIND_SERVICE`; `CAP_NET_ADMIN` обычному proxy listener
не назначаем без подтвержденной необходимости. Запись разрешаем только в
явно нужные runtime/state paths. Это настройки для проверки на реальных
бинарниках, а не уже доказанный готовый sandbox.

Не применяем к AWG запреты `/dev/net/tun` и сетевого администрирования:
создание интерфейса и маршрутов имеет другие требования. Сохраняем профиль
NixOS для AWG/DNS и проверяем эффективные units перед его усилением. Не
назначаем произвольные MemoryMax/CPUQuota/лимиты файлов: они могут превратить
нагрузку в отказ VPN, а ресурсных измерений VPS сейчас нет.

В AdGuard auth-secret сейчас читается группой `acme` (`0440`), хотя обработка
пароля выполняется привилегированным preStart. Рекомендуем сузить чтение
этого секрета до root; доступ самого daemon к ACME TLS key проверять отдельно,
не удаляя нужную supplementary group вслепую. Источник:
[AdGuard module](../clanServices/adguardhome/default.nix). Это рекомендация
для явной миграции secret binding, а не свидетельство раскрытия пароля.

Для plain proxy, не имеющего подтвержденного sd_notify, рекомендуем `Type=exec`
с отдельной проверкой готовности; для Unbound сохраняем native `Type=notify`
и пакет с systemd support. Успешный exec не равен готовому listener, а listener
не равен работающему туннелю. Нельзя добавлять watchdog без поддержки его
уведомлений самим процессом.

Перезапуск — штатный `on-failure`, с задержкой и явной политикой ограничения
частоты в consumer. Не отключаем все лимиты и не строим цикл частых рестартов
на основании неудачного внешнего HTTP probe. Исчерпание попыток должно быть
видно оператору; `network-online.target` не гарантирует доступность VPN bind
или внешнего интернета.

Основание: официальные описания
[systemd service lifecycle](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)
и [execution sandbox](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml).
Документация прочитана на 7 сентября; конкретные директивы и доступ к ресурсам
проверяются на закрепленном systemd/NixOS при реализации.

## Конфигурация, секреты и firewall

Генерация должна быть транзакционной: подготовить закрытые временные файлы,
проверить форму и полную конфигурацию, атомарно заменить рабочий файл и только
затем выполнить поддерживаемый reload/restart. При ошибке сохранить последнюю
рабочую конфигурацию; это не разрешает игнорировать неудачную ротацию секрета.
Все временные файлы удалять и при ошибках. Диагностика parser не должна
печатать строки с credentials; тесты спецсимволов используют фиктивные значения.

Обновление сертификата должно вызывать поддерживаемое действие нужного
сервиса и проверку фактически отданного сертификата. Существование нового
файла не доказывает, что процесс его загрузил. Не заменяем restart на reload,
пока конкретная реализация и NixOS lifecycle не подтверждают поддержку.

Firewall проверяем как итоговую композицию: protocol + destination address
+ port + необходимые интерфейсные ограничения. Исправление правила одного
модуля не отменяет более широкое разрешение другого. Для VPN listener, DNS,
DoH и административного UI должна быть отдельная ожидаемая область доступа.
Нельзя считать открытие 443 только HTTPS-сайтом: на нем может работать proxy.
IPv6 проверяется отдельно; IPv4 rule не является политикой для IPv6.

AdGuard по умолчанию слушает wildcard `::`, а DNS firewall contribution
разрешает доступ на `tailscale0`. Это не доказательство публичного resolver,
но требует отрицательной проверки с WAN и проверки IPv4/IPv6 в итоговой
композиции. Сами module-generated rules допустимы как реализация выбранного
consumer контракта; их наличие не означает нарушения границы владения.
Основание: [NixOS firewall](https://wiki.nixos.org/wiki/Firewall).

## Журналы и наблюдаемость

Рекомендуем обычные эксплуатационные события и ошибки в штатный journal;
подробные connection/access/debug logs включать только для ограниченной
диагностики. IP-анонимизацию не добавляем. Credentials, auth headers, body и
полные клиентские профили в журналы не попадают. Для Mihomo начальный уровень
`warning` уменьшает постоянный поток connection logs; состояние запуска и
рестарты остаются видны через systemd. Содержание ошибок также требует проверки.

По решению от 8 сентября DNS query log сохраняет 7 дней, статистика AdGuard —
90 дней, IP-анонимизация не добавляется. Текущую политику журналов сервисов
сохраняем; предложения назначить произвольные новые сроки сняты. Ее фактические
значения и дисковый бюджет здесь не проверены. Не распространяем срок query log
на весь host journal или сайты Caddy. Изменения лимитов объема и rate limiting
обосновываются измерениями в consumer, а не универсальными числами.
Сейчас AdGuard также создает Caddy access-log contributions для UI и DoH:
их формат может содержать адреса, время и URL; нельзя утверждать, что журналов
доступа вообще нет. Проверять нужно конкретный формат и GET query parameters.
Параметры retention/volume описаны в
[официальном journald reference](https://github.com/systemd/systemd/blob/main/man/journald.conf.xml).

В существующем мониторинге consumer показываем каждую пару server–protocol
отдельно, включая не выбранные Auto. Разделяем признаки:

| Проверка | Что она доказывает |
|---|---|
| Unit/config/listener | Процесс запущен и слушает ожидаемый адрес |
| Authenticated protocol probe | Работают handshake и доступ с probe identity |
| Прикладной download/upload | Через туннель действительно передаются данные в обе стороны |
| UDP relay | Проверяется только для поддерживающих его протоколов; Naive помечается TCP-only |
| Проверка из пользовательской сети | Доступность именно с этой сети в момент теста |

Серверный probe не доказывает доступность из РФ. Клиентский native status
сохраняет согласованное поведение и не подменяется новым контроллером.
Легкие probes и более редкую передачу payload планируем без одновременных
всплесков; фиксируем возраст последнего результата. Не выдаем отсутствие
новых измерений за healthy и не перезапускаем исправный сервер из-за одного
недоступного внешнего test URL.

## Последовательность будущих изменений

1. Приоритет безопасности — обновление Unbound согласно его отдельному аудиту.
2. Исправления validation, секретных файлов и адресной области firewall
   подготовить отдельными обозримыми изменениями с отрицательными проверками.
3. Реализовывать принятые архитектуры по одному протоколу с необходимыми ему
   package changes. AWG3 требует согласованного нового контракта и runtime key;
   одна смена версии бинарника не является миграцией.
4. Для каждого изменения пройти локальный gate, сохранить артефакты,
   затем отдельно проверить состав consumer. Тестовая зависимость Network
   не обновляет автоматически Network в рабочем развертывании.
5. После отдельного разрешения активировать на одной выбранной машине,
   проверить протокол и незатронутые сервисы; следующую машину менять после
   приемки предыдущей. До активации подготовить доступный путь восстановления.

Не обновляем работающие binaries автоматически в обход lock/package authority.
Можно автоматизировать уведомления и подготовку обновлений, но их внедрение
остается отдельным проверяемым действием. Предыдущая NixOS generation должна
сохраняться до приемки; rollback конфигурации не откатывает автоматически
измененные базы AdGuard, списки или секреты. Сохранность/совместимость state
проверяется до обновления, без самовольных backup/restore/prune операций.
Основание: [обновление NixOS](https://nixos.org/manual/nixos/stable/#sec-upgrading),
[flake lock files](https://releases.nixos.org/nix/nix-2.24.14/manual/command-ref/new-cli/nix3-flake.html#lock-files).

Этот документ не разрешает выполнение перечисленных шагов. Полный build gate
для текущего изменения документов не запускался; применены проверки документов.
